## 三、整改原则

1. **先查清线上，再改代码。** R01 未回读 Cloudflare 实际状态前，不做任何部署或回滚操作。
2. **高严重度项阻断账号开放。** R01—R03 未关闭前，不在任何线上环境导入学生名单，也不对外宣布账号可用。
3. **每项有可复现的验收。** 以命令输出、测试或后台回读作为关闭依据；本地通过不等于线上可用。
4. **小步提交，行为与格式分开。** R07 的纯格式化单独提交，不混入逻辑修改。
5. **不改变既有承诺。** 保留案例 ID、课程 slug、匿名自主学习、本地记录导出，以及“脚本版本、任务版本、提交快照不可覆盖”的规则。

## 四、分阶段整改方案

### 阶段 0：查清现状与决策（不改代码）

**R01 部署状态核实**

- 登录 Cloudflare，回读 Pages 项目：生产分支、最近一次生产部署对应的提交、构建命令、Node 版本、Functions 是否启用、`DB` 绑定与环境变量。
- 按回读结果分三种情况处理：
  1. 生产部署仍为 `7a87a40` 或更早：记录事实，后续按阶段 1 完成后再发布。
  2. 生产部署为 `59c6743` 且无 `DB` 绑定：接口统一返回 503，公开导航中的交流、登录入口会显示服务不可用。由用户在 D1 中选择处理方式。
  3. 已绑定数据库：立即核查库中是否已有账号、是否导入过名单、初始密码是否仍有效；若已导入名单，按 R02 先停用未改密账号。
- 今后的工作方式：未验收的服务端功能先进入独立分支和 Cloudflare 预览部署，验收通过后再合入 `main`。
- 验收：`PROGRESS.md` 记录的线上提交、绑定状态与 Cloudflare 后台回读一致，并附回读日期。

**需要用户决策的事项**见第五节；D1—D3 须在阶段 1 开始前确定。

### 阶段 1：上线阻断项与工程底座

按依赖顺序执行：R05 → R04 → R07 → R02 → R03 → R06。

**R05 修复全新克隆下的服务测试**

- 测试开始时以 `recursive` 方式创建 `output/verification/`；同时检查 `tests/`、`scripts/` 中其他写入该目录的位置。
- 验收：`rm -rf output && npm run test:server` 结果为 0 失败（浏览器项在未设置 `FAXUE_BROWSER_TESTS=1` 时跳过）。

**R04 建立持续集成**

- 新增 `.github/workflows/check.yml`：Node 22，`npm ci`，`npm run check`，再运行不开浏览器的 `npm run test:server`。
- 浏览器回归作为第二个作业：安装与锁定版本匹配的 Chromium 后运行 `npm run test:browser`；稳定后再设为必需检查。
- 在 GitHub 为 `main` 开启分支保护，要求检查通过后才能合并（仓库设置，需要所有者操作）。
- 验收：一次拉取请求显示检查通过；故意制造失败的分支显示检查失败并阻止合并。

**R07 统一新增模块的代码格式**

- 引入 Prettier 作为开发依赖，配置为单引号、无尾随逗号，以尽量减少与现有写法的差异；只格式化 `server/`、`functions/`、`lib/api/`、`lib/student-provisioning.js`、`lib/scenes/`，以及 `components/` 和 `app/` 下的新增私有模块。
- 格式化单独提交，不含逻辑修改；新增 `format:check` 脚本并纳入 CI。
- 验收：核心、服务、浏览器测试结果与格式化前一致；`git diff --ignore-all-space --ignore-blank-lines` 只剩标点级变化，并逐文件抽查。

**R02 更换初始凭据方案**（按 D2 的决定执行；以下为推荐方案）

- 预设账号时，服务端为每个学生生成随机一次性激活码（至少 10 位，排除易混字符），只保存哈希。激活码写入仓库外的私有文件（权限 600），由教师私下发放；不生成可推导的初始密码。
- 新增迁移 `0011`：记录初始凭据的过期时间（建议 14 天）。过期后需管理员重新签发；首次登录后强制改密的规则保持不变。
- 管理后台增加“重新签发激活码”操作，并写入审计日志。
- 本机已按旧规则建立的 727 个账号只存在于本地库，正式环境不得沿用；正式导入时按新方案重新生成。
- 验收：服务测试覆盖以下行为——
  - 学号后六位不能登录；
  - 激活码可登录且只能用于改密；
  - 过期激活码被拒绝；
  - 重新签发后旧激活码失效；
  - 重复导入不重置已改密账号。

**R03 密码校验的线上 CPU 实测**（依赖 D3）

- 在预览环境部署后，用 Workers 指标或 `wrangler pages deployment tail` 记录登录、改密请求的 CPU 时间，覆盖单次与 30 次并发两种情况。
- 若采用付费计划：保留 bcrypt，按实测把成本定在 10—12 之间。
- 若只能用免费计划：改用 Web Crypto 原生的 PBKDF2-SHA256（据 Cloudflare 文档，Workers 上限为 100000 次迭代）。哈希值加格式前缀以区分算法，用户下次登录时透明重算，旧哈希继续可验证。
- 验收：预览环境登录 p95 CPU 时间在所选计划配额内，并发登录无 CPU 超限错误；结果写入验收文档，注明计划类型与测量日期。

**R06 确认下载文件名断言**

- 在本机以 `PLAYWRIGHT_CHANNEL=chrome npm run test:browser` 和 `FAXUE_BROWSER_TESTS=1 PLAYWRIGHT_CHANNEL=chrome npm run test:server` 复跑。
- 本机通过：记录为环境差异，并在 CI 中固定与锁定版本匹配的浏览器。
- 本机也失败：检查下载链接的写法（链接未插入文档、对象地址释放时机），修复后复测。
- 验收：CI 浏览器作业中两项测试通过。

### 阶段 2：服务端与页面加固

**R08 减少会话写入并清理过期数据**

- 只有当 `active_at` 距当前时间超过 5 分钟时才更新（空闲过期为 2 小时，精度足够）。
- 在登录成功时顺带删除该用户已过期或已撤销超过 30 天的会话；在低频路径上按条件删除 1 天前的 `rate_limits` 记录。Pages Functions 不支持定时任务，暂不引入独立 Worker。
- 验收：服务测试证明空闲过期、撤销、改密后旧会话失效仍然成立；连续请求只产生一次会话更新。

**R09 降低账号被他人锁定的风险**

- 按“账号 + 来源地址”限流（维持较严格的阈值），另设较宽的按账号总量上限（例如 15 分钟 50 次）防止分布式猜测。
- 验收：更新“同一账号登录频率限制可复现”测试——一个来源超限不影响另一来源正常登录，总量上限仍然生效。

**R10 隐藏回答不再暴露作者**

- 回答不可见且查看者不是管理员时，作者显示名、角色、作者 ID 返回空值。
- 验收：服务测试以普通学生身份读取已隐藏、已删除回答，确认不含作者信息。

**R11 安全响应头与私有页面不收录**

- 新增 `public/_headers`，对静态页面设置：
  - `X-Content-Type-Options: nosniff`
  - `Referrer-Policy: strict-origin-when-cross-origin`
  - `X-Frame-Options: SAMEORIGIN`
  - `Permissions-Policy`（关闭不需要的能力）
- 内容安全策略先以 `Content-Security-Policy-Report-Only` 上线，因为静态导出页面含内联脚本，确认无误后再改为强制执行。
- 在登录、工作区、教师、管理、交流、场景各路由声明 `robots: { index: false }`。
- `_headers` 不作用于 Functions 响应；接口已自行设置 `Cache-Control: no-store`，保持不变。
- 验收：预览环境回读响应头；浏览器回归全部通过；私有页面 HTML 含 `noindex`。

**R13 内容数据迁回 `content/`**：把三类数据改为 `content/` 下的 JSON，由 `lib/content/` 加载器读取；同步更新三个 `verify-*` 脚本和相关测试。数据文件较大，单独提交，并以测试结果前后一致为验收条件。

**R14 PDF 存储策略**（依赖 D4）：短期保持现状，并在 `audit:assets` 中增加总量提示阈值；若后续确需频繁替换 PDF，再评估迁移到对象存储（如 Cloudflare R2）。不改写已有 Git 历史。

**R15 文档同步**：

- 新增简短的根目录 README，内容包括项目简介、常用命令，以及到 `CLAUDE.md`、`PROGRESS.md`、`CONTENT_MAINTENANCE.md` 的链接。

- 本方案各项关闭后，在 `PROGRESS.md` 逐项记录。

- 本方案不包含任何线上部署、回滚或名单导入操作；这些操作均需用户逐次授权。
